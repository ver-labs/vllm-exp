Experiment10: cache implementation overhead
=================================================================

Matched reference versus incremental implementations of LFU + exact partial-prefix caching.
Pinned Qwen3-0.6B, native Mac Metal GPU, FCFS synchronous chunked prefill.
32 physical16-token pages, one slot, batch128, context384, eight outputs/request.
No skip/continue, queue-demand retention, aging or approximate reuse in this A/B.
One diagnostic and three alternating timing rounds per implementation/profile:16 runs.
Both modes use the same new integration hooks and lightweight aggregate timers.
The reference mode retains the previous publication scan and stable allocation sort.
Timings include warmup and empty drain steps; schedule/update timings are inclusive.
Selector/publisher times are nested subsets: do not add them to scheduler totals.
Snapshots copy counters at idle boundaries; background file writes are outside timers.
This instrumentation is enabled equally in both modes; no per-step trace during timing.

Mechanism and correctness
-----------------------------------------------------------------
Partial publication visits new computed prompt ranges and invalidated owned blocks.
Hash removal/promotion/moves dirty affected owners; CoW marks the replaced index.
Free/preemption clears request progress; reset clears progress and ownership.
LFU uses a lazy-invalidated heap keyed by watcher,cached,frequency,free-queue order.
Prepend/append stamps preserve exact stable-sort ties. Heap rebuilds occur at startup,
bounded stale-entry compaction, global aging epochs, and explicit cache reset.
No count, reference, hash identity, or victim-selection policy was changed.
15 integration/differential tests plus4 existing aging tests passed.
Differential pool replay:1500 mixed operations each for LFU and aging LFU.
Both GPU diagnostic decision streams match exactly (physical allocations, evictions,
lookup hits/blocks, scheduled positions and copies; empty drains excluded).
Every timed per-request cached-token count and answer matches its paired reference.
Preemption free/forget/recompute uses the same checked lifecycle; these sequential
GPU workloads do not induce preemption. No preemption-latency claim is made.

Interpretation
-----------------------------------------------------------------
Publishing revisits about87% fewer blocks in these workloads; much of its remaining
time still comes from publishing actual prefix aliases. Selector time decreased in
both GPU profiles. Maintaining dirty owners/free ordering adds work on other paths.
Full scheduler CPU time improved on shift but slightly regressed on stable.
End-to-end median batch time improved slightly (about0.6% shift,1.5% stable).
Paired wall times vary; stable improved in only one of three pairs. Three rounds
on one small-pool workload do not establish a general serving speedup.
Host-only large-pool improvement is not a model-throughput benchmark.
Two excluded setup diagnostics exposed profiler shutdown/completeness issues;
their raw failed summary/log folders remain under results/cache-overhead.
Reports now validate exactly one finish per request, including warmup.
