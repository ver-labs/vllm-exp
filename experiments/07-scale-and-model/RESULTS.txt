Experiment 07: request-count and model-size scaling
===================================================

Completed on 2026-10-21 on the Mac Metal GPU. The combined variant enables
experiments02 (frequency-aware cache eviction),04 (exact partial-prefix reuse),
and05 (bounded unchunked skip/continue) at once. The baseline uses FCFS,
upstream vLLM eviction and coarse 16-token prefix matching. Both variants run
the same editable vLLM source, model checkpoint and workload in each pair.

Two pinned models: Qwen/Qwen3-0.6B at c1899de289a04d12100db370d81485cdf75e47ca;
Qwen/Qwen3-1.7B at 70d244cc86ccca08cf5af4e1e306ecf908b1ad5e. Six scale
points were tested:25,50,100 candidate requests on each model. Every point has
one baseline/combined traced diagnostic and three fresh-server untraced matched
pairs with alternating launch order. All48 serving runs completed successfully.

Each count has half long prompts (rounding up), then half short prompts. Prompt
lengths are exactly320 and64 chat-template tokens in each model. Every candidate
generates64 tokens; eight blockers generate128 tokens each. Candidate arrivals
are10ms apart. The same eight running slots,256 physical16-token KV pages,
512-token context/batch budget, FCFS, seed0, synchronous unchunked prefill,
native Metal worker and system prompt apply at every point. This new25-request
point replaces historical25-request timing in scale comparisons: those older
studies had different blockers and arrival gaps.

Negative change means combined finished sooner. Completion time is measured
from candidate release until the last candidate finishes; server startup and
the one-token warmup are excluded. Cache hits are sums of candidate cached
prompt tokens from the API; each value was identical across all diagnostic and
timed runs for its respective variant and scale point.

The combined variant was faster in exactly8 of18 pairs. These exploratory
runs establish cache and scheduling behavior, not a reliable overall speedup.
Absolute 0.6B batch time was even lower at50 requests than at25 despite twice
the candidates. Machine or run variability is large enough that these medians
must not be treated as a clean performance scaling curve.

The fairness tradeoff is clearest at25 requests. Median first text for long
prompts worsened4.58->8.21s on0.6B and8.60->16.61s on1.7B, while short
prompts improved8.59->6.14s and16.31->12.67s. At50 and100, group medians
changed in the same direction as the overall runtime for each point; no
universal long/short latency benefit can be claimed.

Diagnostics confirmed all candidate requests waiting together at every point.
The baseline logged6 unchunked budget stops at every point. Combined logged
28 skip events at25 requests and64 at50 and100, plus2 budget stops at every
point. There were zero preemptions. Combined
candidate cache hits increased by212 at25,441 at50 and885 at100 for both
models. These exact results show the mechanisms operate with both model sizes,
but do not isolate the individual contribution of each policy.

Exact candidate-answer agreement across the three pairs:
  0.6B/25:20/25 in each; /50:50/50 in each; /100:100/100 in each.
  1.7B/25:13/25 in each; /50:50/50 in each; /100:100/100,99/100,95/100.
The benchmark fixes token counts, not semantic quality. Answer differences can
arise from batching or prefill changes under low-precision execution; no
quality-parity claim is made.

Conclusion: this is a reproducible six-point baseline for further scheduler
experiments. More requests and a larger model did not turn the combined policy
into a consistent throughput improvement. Retain per-group latency, cache hits,
paired times and answer comparison whenever changing the algorithm.
